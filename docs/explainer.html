Android UI tests · written by agents · accepted by proof

Would this test actually turn red if the feature broke?

An AI agent can write an Android UI test in minutes. ProofLoop accepts the test only after it passes on every clean run of the good build and fails, at the expected step, on builds with the feature deliberately broken. Plain code gives the verdict. No model does.

The problem

A test that passes tells you little. The agent that wrote it also decides what "correct" looks like, so it can assert something too weak to ever fail, or lean on a wait that makes it pass for the wrong reason. A green run only shows the test did not fail this time.

The question that matters comes after: if someone breaks the feature, does this test go red, and at the step that tests the feature? ProofLoop asks that directly by breaking the feature on purpose and watching.

The gate

For one acceptance criterion, a flow is proven only when both hold:

Good build
10 clean runs from a reset app. All must pass.
Bug: weekdays off by one
C1C2C3 failedC4
Must fail at C3, the checkpoint that tests days. A crash or a failure elsewhere does not count.

The run order saves time on failures. The runner does one good run, then each proof bug, then the remaining nine good runs. A test that misses a proof bug is rejected after about two runs instead of eleven.

Bugs come in two roles. Proof bugs select the test. Held-out bugs run after the verdict and never change it; they measure whether the test also catches defects it was not tuned for.

Why "at the expected step" matters

Every flow carries checkpoint markers. A failure maps to the marker it happened under: setup before the first, a checkpoint, or action (a tap that failed). Only a failed assertion at the expected checkpoint counts as catching the bug. One seeded bug crashed the app at launch; the test "failed" and the gate refused to count it.

How it works

Three parts. The agent does the creative work. The runner does everything that must be the same every time.

agent · skill1. Plan checkpointsTurns the criterion into numbered, observable conditions.
human2. Approve the planproofloop approve hashes plan.md and the bug list. If either changes, or the flows' checkpoints differ from the plan, the runner refuses.
agent · skill3. Explore and writeReads the app map, explores the good build with Maestro, writes the flow. Never sees the bug builds.
runner4. Check the flowCommand allowlist, checkpoint mapping, no waits hiding a checkpoint, no checkpoint that cannot fail. --fix repairs the mechanical errors.
runner5. Prove itResets the app, pins the clock, and runs the good build and each bug build. Good runs can spread over several emulators. Good run 1 is recorded on video.
runner6. Verdict and reportSeven possible verdicts. The record hashes every flow, plan and APK it used. Only proven can become a pull request, and only while the flow still matches its hash.
  • The proofloop skill guides Claude Code through the steps above and at most two evidence-based repairs.
  • The runner is a Python standard-library program (proofloop): flow checker, app reset, clock and time-zone pinning, read-only sound probes, repeated runs, verdict, run record, report, publishing.
  • The app-map skill explores an app once and records its screens, actions and rules, so the next session does not start from zero.

Why the runner owns device state

The first proof was rejected as flaky twice. The cause was not the app: a data clear left a pending "remove task" that killed the freshly launched process 68 to 185 ms after it started. Moving reset into the runner, with a wait for the old task to go, gave 0 hangs in 40 launches. The runner also pins the clock (Maestro flows cannot) and reads sound state with probes (quiet or normal, from dumpsys audio, do-not-disturb and ring volume).

A worked example

Criterion for Quiet Hours, a sound-scheduling app: a Weekdays schedule appears on Home with its title, "Weekdays", and the correct next start. The clock is pinned to Wednesday 18 Nov 2026, 08:00.

CheckpointWhat it assertsGood buildWeekdays off by oneNext start skips today
C1The wizard opens from "Add Schedule"passpasspass
C2The title is listed on Homepasspasspass
C3The day summary reads "Weekdays"passfailpass
C4Status reads "Next: Today 9:00 AM"passnot reachedfail

The first bug (Tue to Sat instead of Mon to Fri) is the proof bug and is caught at C3. The second is held out and is caught at C4. Without the pinned clock, the held-out bug passed the test on a Saturday: the next start of a weekday schedule is Monday whether or not today is skipped.

The checkpoint markers are comments in an ordinary Maestro flow:

# checkpoint: C3 the day summary reads "Weekdays"
- assertVisible: "Weekdays"

What a fresh agent gets wrong

Six fresh agent sessions each wrote a test for the same new criterion. All six passed the good build 3 of 3. None was proven. Every one put a wait for a plant name above the checkpoint marker. On the bug build the garden was empty, so the wait failed at setup, which the gate does not count.

Wait above the marker
- extendedWaitUntil:
    visible: "Avocado"
# checkpoint: C1 listed
- assertVisible: "Avocado"
Marker above the wait
# checkpoint: C1 listed
- extendedWaitUntil:
    visible: "Avocado"
- assertVisible: "Avocado"

The flow checker now rejects the first form. Re-running six fresh sessions with that rule: 6 of 6 proven. Waits on a screen anchor from the app map stay allowed, because that text is always on the screen.

proofloop check --fix now makes that move itself. A flow written with the round-1 mistake, plus a bare launchApp, was fixed in code with no agent repair and proven 3 of 3, with the bug caught at its checkpoint. A second rule rejects a checkpoint that only repeats text already checked with no action in between: it cannot fail. It fired on two of six new authors, and each fixed it in one step.

App maps: memory between sessions

An app map is a markdown file per app: screens with their always-present text (anchors), the actions between them, and notes of four kinds (precondition, rule, lookup, hazard). The idea comes from a talk on agent test memory, where a map like this cut an agent's repeated mistakes from 87 to 0. Here it is used when a test is authored.

## screen: saved
anchors: "Routine saved", "Done"
- tap "Done" -> home
- rule: "Next start" and the end-settings sentence are one text
  element; a locator must continue past the first line: "Next start: ....*"

Does a map that grows help?

On Quiet Hours, one author hit the multi-line text failure and wrote the fix into the map as two lines. Six later authors then wrote a similar test, three with the original map and three with the grown one.

All three authors with the original map failed their first run on that quirk. None of the three with the grown map did. The author's flow became a fourth checked-in task.

Keeping tests proven

A proof is only true for the build it ran on. Each task now keeps a proof history. On 2026-11-23 the three Quiet Hours tests were re-proved on the app's newest build, 31 commits later:

Nov 14-17
proven on e4ba3eb, 10/10 each
Nov 23, new build
0 / 10 all three. New one-time tip bubbles dim Home and the wizard, so Maestro cannot see the text the flows wait for.
Repair
Optional taps on "Skip|Got it" before the blocked waits. No checkpoint changed. The app's own fix used runFlow, which the allowlist blocks.
Nov 23, re-proof
proven 10/10 each. One task first came back 4/10: a wizard tip appeared on only 6 of 10 runs, a race one green run would hide.

proofloop history reports this as shelf life: "first proven 2026-11-14 … stopped being proven on 2026-11-23 after 8 days; proven again (flows changed)". proofloop retro names the 0/10 failure a broken setup step, not flakiness.

Real bugs, not just seeded ones

proofloop mine-bugs finds fix commits in the app's history. The commit before a fix is a real, unseeded bug build. The one that differs from the good build by that bug alone, a VIP Do Not Disturb bug, is not caught by any task, because none exercises VIP calls. That is a measured coverage gap, and it is the next test to write. proofloop from-fix has already scaffolded it from the fix commit.

The proof found a real bug. The Quiet Hours build everyone called good cached its Home status line without the time, so while Home stayed open it kept showing "Next: Today 9:00 AM" through the whole active window. The end-alarm task failed on the good build. It was fixed in the app and verified red then green on the device.

"Passed 10/10" bounds the true flake rate below 26% at 95% confidence. Over all 40 runs the bound is about 7%. Neither is zero, and every report says so.

What went wrong along the way

  • The plan was to build a generator that already existed. Research first found Maestro's own MCP server, and the project became a proof gate instead.
  • The unit tests "failed" 117 times on every build. Android Studio's bundled Java 25 cannot run Mockito. A failure identical on the good build is not a test result.
  • A status check deleted the alarm it was observing: Maestro's launchApp force-stops the app, and Android cancels a force-stopped app's alarms. The checker now requires stopApp: false.
  • A held-out bug escaped because the clock was not pinned. Time-dependent checkpoints need a pinned clock and expected text read from the app.
  • mobile-mcp and Maestro cannot share a device: each holds the only UI-automation connection.

Almost every rejection came from the harness, not from the agent's flows. The full log is in the repo.

Using it

You need Python 3.11+, adb, the Maestro CLI and one emulator or device.

git clone https://github.com/samir-sayyed/proofloop && cd proofloop
pip install -e .
brew tap mobile-dev-inc/tap && brew install mobile-dev-inc/tap/maestro
claude mcp add maestro -- maestro mcp
cp -R skills/proofloop skills/app-map ~/.claude/skills/
proofloop doctor

In Claude Code, ask for a test in plain language: "Prove a test that a Weekdays schedule shows up on Home." The skill plans checkpoints, asks you to approve, explores, writes the flow, runs the proof, and offers a pull request only if the verdict is proven. Or run the commands yourself:

CommandDoes
proofloop check TASK [--fix]Check the flows, and fix the mechanical errors. No device needed.
proofloop approve TASK --by NAMEBind a human's approval to the plan and bug list.
proofloop prove TASK [--devices A,B] [--snapshot S]Run the proof; write the record, report, video and history line.
proofloop eval DIRProve every task: verdicts, repairs, author and tokens.
proofloop history TASKShelf life: every proof, and the build it stopped on.
proofloop mine-bugs REPO --after GOODReal fix commits whose parent is a held-out bug.
proofloop retro PATHSGroup rejections by cause, with the rule that addresses each.
proofloop next APP_DIRBackfill queue: untested map rules, screens, actions.
proofloop from-fix REPO SHARegression task from a fix: good is the fix, bug is its parent.
proofloop publish RECORD --repo APPCommit a proven test on a branch; --push opens a PR, at most 3 waiting. Never merges.
proofloop prepare TASKPut the device in the start state for exploring.
proofloop map MAP [FLOWS]Check an app map and list untested screens.
proofloop doctorCheck adb, device, Maestro, free space.

A task is a JSON file naming the good build, the seeded-bug builds with the checkpoint each must fail at, the device state (clock, time zone, permissions) and the steps. Sunflower is fully reproducible from the repo. The Quiet Hours tasks are worked examples, because that app's source is not in the repo.

Safety and limits

  • The flow checker blocks scripts, links, nested flows, retries, other apps, force-stops and device-state changes, in code, before any device action.
  • Installs, data clearing, permissions, clock and probes happen in the runner, outside the agent's tools. Screen text is data, never instructions.
  • A human approves the plan and the bug list. If the owner delegates approval in chat, the record says so. Unproven tests never open a normal pull request. ProofLoop never merges.
  • Small suite: 4 tasks, 2 apps, 7 seeded bugs (6 hand-written) and 2 real ones from the app's history.
  • Baselines cover one criterion, three trials per arm. Token cost is measured for Claude Code authors only.
  • One device image and one host: Pixel 8 emulator, Android 14, macOS.
